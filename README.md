# llm-agent-lab

> LLM과 AI 에이전트가 내부적으로 어떻게 동작하는지 직접 확인하기 위한 개인 학습용 저장소다.
> 프레임워크부터 쓰면 무엇이 자동으로 처리되는지 알 수 없기 때문에, 먼저 순수 SDK로 HTTP 호출 한 번부터
> 시작해 툴 콜링과 에이전트 루프를 손으로 구현하고, 그 다음에 같은 것을 프레임워크로 다시 짜면서
> 프레임워크가 무엇을 대신해주고 무엇을 감추는지 비교한다. 백엔드 개발은 해왔지만 AI는 사용자 입장에서만
> 써본 상태에서 출발하는 기록이라, 결과물보다 "왜 이렇게 동작하는가"를 남기는 데 목적이 있다.

## 📚 단계 구성

| 단계 | 주제 | 무엇을 이해하려는가 |
| --- | --- | --- |
| `01-raw-api` | 순수 API 호출 | LLM은 상태를 갖지 않는다. 대화가 이어지는 것처럼 보이는 이유는 매 요청마다 이전 메시지를 전부 다시 보내기 때문이라는 것을 직접 확인한다. messages 배열, role, 토큰 사용량이 실제로 무엇인지 체감한다. |
| `02-tool-calling` | 툴 콜링 / Structured Output | 모델은 툴을 "실행"하지 않는다. 어떤 함수를 어떤 인자로 부르라는 JSON을 반환할 뿐이고, 실제 실행과 결과 전달은 내 코드의 책임이라는 경계를 확인한다. 스키마를 강제해 응답 형태를 고정하는 Structured Output도 같은 맥락에서 다룬다. |
| `03-agent-loop` | ReAct 루프 직접 구현 | "에이전트"라는 것이 결국 툴 콜이 없을 때까지 도는 while 루프라는 것을 확인한다. 파일 읽기/쓰기/셸 실행 툴을 붙여 최소한의 코딩 에이전트를 만들고, 종료 조건·에러 처리·컨텍스트 누적을 직접 설계해본다. 스트리밍 응답 처리도 여기서 다룬다. |
| `04-rag` | 임베딩 / 청킹 / 유사도 검색 | 검색 증강이 마법이 아니라 텍스트를 벡터로 바꾸고 코사인 유사도로 고른 조각을 프롬프트에 끼워 넣는 일이라는 것을 확인한다. 청킹 방식과 검색 품질이 답변에 어떻게 직결되는지 본다. |
| `05-frameworks` | 프레임워크 재구현 | 03에서 손으로 짠 에이전트를 프레임워크로 다시 구현하며 1:1로 대응시킨다. 편해지는 대신 무엇이 보이지 않게 되는지가 관심사다. |
| └ `langchain` | AgentExecutor | 내가 짠 while 루프가 AgentExecutor의 어느 부분에 해당하는지, 프롬프트와 파싱이 어디에 숨어 있는지 확인한다. |
| └ `langgraph` | 상태 머신 | 같은 루프를 노드와 엣지로 다시 표현한다. 루프를 그래프로 보면 분기·재시도·중단점이 어떻게 달라지는지 확인한다. |
| `06-mcp` | MCP 서버 구현 | 툴을 코드에 직접 박는 것과 프로토콜로 분리해 노출하는 것의 차이를 확인한다. 서버를 직접 만들어 클라이언트가 툴 목록을 발견하고 호출하는 과정을 본다. |

같은 에이전트를 `03-agent-loop` → `langchain` → `langgraph`로 세 번 구현하는 것은 의도적이다.
직접 짠 코드가 기준선이 있어야 프레임워크가 추상화한 부분을 알아볼 수 있기 때문이다.

## ⚙️ 환경

- Python 3.13
- 패키지 관리는 uv (`pyproject.toml` + `uv.lock`)
- LLM 호출은 OpenRouter (OpenAI 호환 엔드포인트라 `openai` SDK를 그대로 사용)

```bash
# 의존성 설치
uv sync

# 실습 실행
uv run 01-raw-api/<파일명>.py
```

API 키는 `.env`로 관리한다. 저장소 루트에 아래 형태로 둔다.

```
OPENROUTER_API_KEY=sk-or-...
OPENROUTER_BASE_URL=https://openrouter.ai/api/v1
```
